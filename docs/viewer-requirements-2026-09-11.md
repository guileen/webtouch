# UWS 观看小窗（Viewer）需求说明 — 2026-09-11

> 用途：对外咨询/评审用的需求描述（自包含、脱敏、无内部路径与密钥）。面向对象：无本项目上下文
> 的技术评审者（人或其他 AI）。

## 0. 一句话
给一个浏览器自动化引擎加一个「始终可见、但绝不打扰」的观看小窗：用户能像看虚拟机一样
围观 AI 在真实 Chrome 里操作网页；需要时点一下就展开，并能一键切到真实浏览器窗口。

## 1. 角色与背景
- **被改造对象**：自研浏览器自动化引擎（下称 UWS），由多个 AI Agent 调用，用真实 Chrome 执行
  网页操作：打开页面、点击、输入、滚动、抓取、截图、视觉判断等。
- **现状痛点**：Agent 在操作时用户看不见过程；唯一的可见物是一个真实 Chrome 窗口，而它会被
  带到前台，打断用户正在打字/看别的东西 —— 用户明确要求"不打扰、不打断我的当前工作状态"。
- **目标体验参照**：类似 ChatGPT 桌面端的「内置浏览器小窗 + 点开落到审阅区」那种交互。

## 2. 硬性要求（不可妥协）
- **R1 不抢焦点**：小窗在任何时刻都不得抢走键盘焦点、不得把窗口抬到前台；用户打字、点击
  其他应用完全不受影响。真实 Chrome 窗口在后台执行操作时，同样绝对禁止触发系统级前台化。
- **R2 浏览器一致性（红线）**：被操作的页面必须由**真实 Chrome** 渲染与执行（DOM/JS/布局/
  登录态/可访问性树全部真实），不得用 WebView 或模拟渲染替代，也不得在页面内部注入干扰 DOM。
- **R3 始终可见**：小窗悬浮置顶于其他窗口之上，不被遮挡（用户要"瞟一眼就能看到"）。
- **R4 点击才展开**：小窗本身不拦截用户的正常操作；用户点击小窗 → 展开为正常窗口
  （展开后可以正常交互、可以获取系统焦点）。
- **R5 会话独立**：多个 Agent 各自一条会话，不得互相争抢 Chrome 进程/标签页/操作权；
  用户能清晰看出"现在是哪个 Agent 在操作"。
- **R6 观看壳不用 WebView**：观看界面用原生窗口绘制（macOS AppKit/CALayer），零 WebView、
  零内嵌 HTML 渲染，确保观看壳自身极其轻量且内存可控。
- **R7 低延迟与低打扰**：画面流与光标动作的端到端延迟保持在平滑感知范围（≤150ms），
  空闲时自动降低帧率以节省 CPU 与电池。

## 3. 交互规格
1. **小窗形态**：把被操作的页面按比例缩小显示（原尺寸的 1/4 ~ 1/8，默认约 320×200 ~ 400×250），
   常驻屏幕一角，可拖动吸附边缘、可固定（pin）某个会话。
2. **原生放大虚拟光标（Overlay 自绘）**：
   - 用一个大号高对比度虚拟指针表示"AI 的鼠标"，由 Viewer 原生层（CALayer）在画面之上叠加绘制，
     实时跟随真实操作坐标移动，带平滑补间动画；
   - 点击/双击/拖拽时有原生波纹涟漪反馈与按键态高亮 —— 用户观感是清晰感知"AI 在点这里"，
     但不放慢实际执行节奏；
   - **关键原则**：不在真实页面 DOM 内注入任何指针元素，避免破坏页面原有样式或触发反爬检测。
3. **会话状态标签**：小窗顶部/底部悬浮极简半透明标签：显示当前 Agent 名称/会话标识 + 页面 Title/URL
   + 正在执行的动作（如「正在输入搜索词…」「等待页面加载…」）。
4. **平滑展开**：点击小窗主体或展开图标 → 动效展开为标准尺寸窗口（同一会话画面），
   可一键收回小窗态。
5. **切真窗口（物理兜底）**：小窗/展开窗上一键直达：把被操作的真实 Chrome 窗口带到系统前台 —— 
   此时看到/操作的是 100% 原生 Chrome（包含文件选择器、下载弹窗、扩展图标、地址栏等全部原生 UI）。
6. **多会话调度**：默认全局单小窗，跟随最近活跃会话自动切换视图；支持列表切换或 pin 固定某会话；
   多会话并列多窗列为待定项。

## 4. 技术前提与已知约束（已实测/已确认）
- **真实 Chrome 窗口本身做不到"置顶 + 不抢焦点 + 缩放显示"**：
  - CDP 仅支持窗口状态控制（normal/minimized/maximized/fullscreen），无操作系统层级（always-on-top）控制；
  - 尝试用渲染缩放（`Emulation.setDeviceMetricsOverride` 的 scale 参数）会直接改变页面的 viewport 尺寸，
    污染页面流式布局、媒体查询与可访问性树（AXTree），对严谨的"真实自动化"底座不可接受；
  - **推导结论**：小窗必须采用**「独立自绘原生窗口 + 页面画面流 + 原生事件叠加层」**，绝不能是 Chrome 窗口本身。
- **画面流机制与反节流（Screencast）**：
  - 画面来源：CDP `Page.startScreencast`（JPEG 格式，quality/maxWidth/maxHeight/everyNthFrame 可调）；
  - **关键机制：反压 ACK**：客户端收到 `Page.screencastFrame` 后必须向 Chrome 回复 `Page.screencastFrameAck`，
    否则 Chrome 会暂停发送后续帧；
  - **后台遮挡节流避坑**：Chrome 在窗口不可见/完全被遮挡时，默认启用 `CalculatePageOcclusion` 导致渲染降频或挂起；
    启动真实 Chrome 时必须配置防节流启动参数（如 `--disable-backgrounding-occluded-windows`、
    `--disable-background-timer-throttling`、`--disable-renderer-backgrounding`）。
- **画面局限与兜底边界（诚实边界）**：
  - screencast 仅抓取网页渲染区域的内容，不包含操作系统原生弹窗（文件选择器、权限弹窗、原生右键菜单、地址栏等），
    且系统原生鼠标指针不会出现在流中；
  - 因此：虚拟光标必须在原生壳中自绘，遇到原生弹窗或需人工接管时，「切真窗口」作为确定性兜底。
- **运行环境与架构边界**：
  - 环境：macOS 13+；Swift / Clang 工具链就绪；
  - 进程拓扑：UWS 自动化引擎（后台守护进程）负责管理 Chrome CDP，捕获帧流与 Agent 动作坐标；
    Viewer 壳（独立原生 Swift/AppKit 进程）通过轻量本地 IPC（Local WebSocket / Unix Domain Socket）
    订阅帧流与状态，完全解耦；
  - 可嵌入性：Viewer 视图层设计为标准 AppKit View 组件，将来自家桌面 App 可直接以原生组件形式嵌入。
- **会话隔离现状**：
  - 引擎已具备命名上下文路由能力（每会话独立标签页/窗口，Action 按 SessionID 路由）；
  - 默认复用用户已登录的调试 Chrome Profile（保留登录态为核心价值），同时支持开关切换为完全独立的 Chrome 实例。

## 5. 分期
- **P1（低风险原型与协议闭环）**：
  1. UWS 引擎开启 `Page.startScreencast`，输出本地轻量帧流与动作坐标事件流（JSON）；
  2. Swift 原生极简小窗原型：验证 `NSPanel`（`.nonactivatingPanel`）、置顶、零焦点抢占；
  3. Viewer 原生 Overlay 叠加绘制放大虚拟光标与点击涟漪（零 DOM 侵入）；
  4. 验证核心验收标准：用户在其他应用正常打字，焦点完全不丢失。
- **P2（核心体验完整化）**：
  1. 小窗平滑展开为大窗口 / 收回小窗动画与交互；
  2. 一键切真窗口（通过 macOS 系统 API 将真实 Chrome 激活到前台）；
  3. 会话标签、状态提示与多会话切换/Pin 机制；
  4. Chrome 后台运行加固（防休眠、防渲染节流断流、动态帧率调节）。
- **P3（进阶能力与嵌入）**：
  1. 小窗内直接反向操作（小窗内鼠标点击/滚动按缩放比例逆向映射，通过 CDP 回灌给 Chrome）；
  2. 封装为独立 Swift Package / 框架，供自家宿主 App 无缝嵌入；
  3. 动作历史与思考时间线展示面板。

## 6. 想请教的问题（咨询重点）
1. **macOS 非激活置顶面板的最佳实践与陷阱**：
   - 采用 `NSPanel` + `.nonactivatingPanel` 样式，配合 `windowLevel = .floating` 和 `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]`；
   - 在小窗态下如何彻底屏蔽 Key Window 获取（如重写 `canBecomeKeyWindow -> false`），而在用户明确点击展开后如何优雅、平滑地转为正常可获取焦点的窗口？
   - 多显示器切换与全屏应用（Spaces）切换时是否有窗口闪烁或坐标错位的已知系统级 Bug？
2. **CDP `Page.startScreencast` 的真实工程开销与调优**：
   - 在小窗缩小显示场景（例如目标视口 1280×800，小窗显示 320×200）下，`maxWidth`/`maxHeight`/`quality` 设为多少能在保真度与 CPU/内存之间取得最佳平衡？
   - 连续运行数小时是否有内存泄漏或 WebSocket 缓冲区积压隐患？`Page.screencastFrameAck` 的流控反压策略怎样最稳健？
3. **画面外送替代方案的深度对比（Screencast vs macOS ScreenCaptureKit）**：
   - 若在 macOS 上直接采用系统级 `ScreenCaptureKit` (SCK) 定向截取真实 Chrome 窗口：
     - 能否解决原生弹窗/下拉菜单不可见的问题？GPU 直接渲染到 Metal/IOSurface 的性能和 CPU 占用是否显著优于 CDP JPEG 编解码？
     - 但 SCK 强制要求用户授予 macOS 系统级「屏幕录制」权限，且如果 Chrome 窗口被遮挡或在非当前桌面，SCK 的抓取表现如何？两者的综合权衡建议是什么？
4. **多会话同时推流的伸缩性成本**：
   - 若 3~5 个 Agent 同时并行操作不同标签页，是为每个 Session 维护一条独立的 screencast 流在本地按需切换，还是有更低开销的多路管理方案？
5. **用户反向操作（点击小窗转发给 Chrome）的已知技术坑**：
   - 当小窗画面存在缩放、页面存在滚动偏移（`scrollOffsetX/Y`）与设备像素比（DPR/Retina）时，点击坐标映射到真实页面坐标的对齐精度有哪些陷阱？
   - 文本输入与输入法（IME）转发在非真实激活状态下如何处理？

## 7. 验收（怎么算成了）
- **绝不抢焦点**：用户一边在其他软件（终端、IDE、文档）打字，后台 Agent 一边在操作网页：用户打字不中断、光标不失焦，小窗实时可见且虚拟指针流畅运动。
- **无感与直达**：点击小窗能平滑展开为大窗口查看细节；点击一键直达可瞬间切到真实 Chrome 窗口并接管。
- **多会话清晰**：多个 Agent 并发执行时，标签与会话指示清晰，小窗可随最新活跃会话平滑切换或被 Pin。
